# Hybrid AI–NWP Adaptive Forecast Blending System

**Team BITCODE · Smart India Hackathon 2026 · Problem Statement 26081**

An end-to-end prototype that adaptively blends ECMWF IFS (physics-based NWP), ECMWF ENS
(ensemble) and ECMWF AIFS (AI-based forecast) using a regime-aware LightGBM gate + a
PyTorch spatial U-Net, protects extreme signals from over-smoothing, verifies results
against ERA5/GPM reference data, and explains every blend to the user.

See `IMPLEMENTATION_PLAN.md` for full architecture, data flow, and design decisions
(including the documented "Demo Mode" simplifications — this runs fully offline for
SIH judging).

## Quick start (recommended: Docker)

```bash
cp .env.example .env
docker compose up --build
```

- Backend: http://localhost:8000 (docs at http://localhost:8000/docs)
- Frontend: http://localhost:5173

## Quick start (manual / local dev)

### 1. Backend

```bash
cd backend
python3 -m venv venv && source venv/bin/activate     # optional but recommended
pip install --break-system-packages -r requirements.txt
# CPU-only torch, if the default `pip install torch` pulls CUDA packages on your machine:
#   pip install torch --index-url https://download.pytorch.org/whl/cpu
uvicorn app.main:app --reload --port 8000
```

The first startup trains the LightGBM adaptive gate on a simulated skill archive
(sub-second) and initializes the U-Net — this happens once per process start.

SQLite database is created automatically at `backend/data/app.db`.

### 2. Frontend

```bash
cd frontend
npm install
cp .env.example .env      # VITE_API_URL=http://localhost:8000/api
npm run dev
```

Open http://localhost:5173, click **Explore Forecasts → Enter Demo Mode**.

## Running tests

```bash
cd backend
pip install --break-system-packages -r requirements.txt   # includes pytest, httpx
python3 -m pytest ../tests/test_backend_pipeline.py -v
```

All 22 tests (data loading, preprocessing/regridding, regime detection, weight
safety/redistribution, extreme-event scaling, verification metrics, and live API
endpoints via FastAPI's TestClient) pass against this codebase.

## SIH judging demonstration script

1. Landing page → **Explore Forecasts**
2. Dashboard → select Region: Tamil Nadu, Variable: Rainfall, Lead: +24h,
   Scenario: Convective Heavy Rainfall → **Run Adaptive Forecast**
3. Watch the pipeline animation execute (ingest → align → regime → weight →
   blend → extreme → verify) — these are real backend calls, not a frontend timer
4. Open **Model Insights** → see the dynamically computed IFS/ENS/AIFS donut +
   "Why did AIFS receive higher weight?" explanation
5. Open **Alerts** → see extreme-event risk across monitored regions
6. Open **Analytics** → compare IFS / ENS / AIFS / Fixed Blend / Adaptive Blend
   on MAE, RMSE, CRPS, F1, and see the computed skill-improvement percentage

## What's real vs. what's demo-simplified

Everything downstream of data ingestion is real, executed computation:
QC → regridding → feature engineering → regime detection (deterministic rules
over computed features) → LightGBM adaptive gate (trained at startup) → PyTorch
U-Net (real forward pass) → extreme-event logistic heads → verification
(MAE/RMSE/CRPS/POD/FAR/CSI/F1/Brier, computed against ERA5/GPM demo-truth
arrays) → explainability → SQLite persistence.

The one deliberate simplification, disclosed in the UI and in
`IMPLEMENTATION_PLAN.md`, is that IFS/ENS/AIFS/ERA5/INSAT/GPM inputs are
generated by a physically-plausible synthetic demo engine rather than
downloaded from live ECMWF/ISRO/NASA feeds (no internet access is available/
required for SIH judging). The adapters in `backend/app/data/` are the only
place that would need to change to plug in real feeds later.

## No GraphCast

GraphCast is not used or referenced anywhere in this project. The AI-based
forecast source throughout is **ECMWF AIFS**.
